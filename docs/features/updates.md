# Application updates and releases

Vibe DB has one release source and three installation paths:

| Platform | Distribution | Update action |
| --- | --- | --- |
| Windows 10/11 x64 | NSIS installer from this repository's Releases | Settings → Updates downloads and starts the next installer |
| Windows 10/11 x64, portable | ZIP holding `vibe-db.exe` alone, from Releases | Replace the exe by hand with the next ZIP's |
| macOS 12+ Intel/Apple Silicon | ZIP from Releases, or the Cask in `Casks/vibe-db.rb` here | Homebrew runs `brew upgrade --cask vibe-db`; a direct download is replaced manually |
| Linux x64 | `.tar.gz` from Releases | Settings → Updates opens the release page; the archive is unpacked over the previous copy |

The source repository is public, so the releases and the Homebrew Cask live in it and the workflow
needs nothing but the built-in `GITHUB_TOKEN`. No database profiles, secrets or history are stored
inside the installed application directory, so installing a new version does not migrate or remove
them.

The Cask is in this repository rather than in a `homebrew-*` one, so tapping it names the URL:

```sh
brew tap khanhsnd/vibe-db https://github.com/khanhsnd/vibe-db
brew install --cask khanhsnd/vibe-db/vibe-db
```

## Moving off the two old repositories

Up to `1.2.2` the source was private, and releases went to `khanhsnd/vibe-db-releases` and the Cask to
`khanhsnd/homebrew-tap`, both written with the `RELEASES_TOKEN` secret. **A copy built before the move
still asks `vibe-db-releases` for its update**, and a Homebrew install still reads `homebrew-tap`, so
the release workflow's `legacy` job keeps mirroring each release to both while that secret exists —
the release itself and a Cask pointing at the ZIP here. Once the installs that matter run a version
built after the move:

1. Delete the `RELEASES_TOKEN` Actions secret. The `legacy` job then skips every step.
2. Delete `khanhsnd/vibe-db-releases` and `khanhsnd/homebrew-tap`, and the token itself.
3. A Homebrew user re-taps once: `brew untap khanhsnd/tap`, then the two commands above.

A copy that was never updated past the move has to be replaced by hand after step 2.

## The portable Windows build

`vibe-db-<version>-windows-x64-portable.zip` holds the very `vibe-db.exe` the installer copies into
Program Files — a Wails binary is self-contained, with the frontend embedded in it, so the installer
adds only a Start-menu entry, an uninstaller and an elevation prompt. Unzipped anywhere, it runs as it
is, without administrator rights. It still needs the WebView2 runtime, which Windows 11 and an
up-to-date Windows 10 already have; where it is missing, the installer is the build that fetches it.

Portable means *no installation*, not *no trace*: profiles, history and snippets live in the user's
configuration directory and secrets in Windows Credential Manager, exactly as for an installed copy, so
the two share them. Settings → Updates in a portable copy still offers the installer; a reader who
wants to stay portable downloads the next ZIP and replaces the exe instead.

## Publishing a version

Use a three-part semantic version and push a tag:

```powershell
git tag v1.0.0
git push origin v1.0.0
```

The workflow builds a Windows x64 NSIS installer and a portable Windows ZIP, a universal macOS app and a Linux x64 archive, computes
SHA-256 checksums, publishes the assets as a release of this repository with release notes generated by
GitHub, and commits the updated `Casks/vibe-db.rb` to `master`.
A release is not complete until every publish job is green.

What a reader does with those assets is the Install section of [the README](../../README.md#install).
A Homebrew install is updated with:

```sh
brew upgrade --cask vibe-db
```

The app's Settings → Updates page checks the GitHub release API, and **a release is an update when its
version is not the one running — not when it is a higher one**. The release channel decides which version
this app is meant to be on, so a version line corrected downwards is offered like any other release
instead of stranding every copy built from the mistake; a version published *below* an existing install
is therefore an ordinary update and the page says so. What GitHub calls the latest release is the one
published most recently rather than the highest tag, which is the same rule read from the other end.
Builds before `0.1.8` accepted a higher version only, so a copy installed from one of those has to be
replaced by hand once — the rule below lives in the running build and cannot reach it from a release it
refuses to see. A Windows update is downloaded and its
checksum is checked against `checksums.txt` before the NSIS installer starts and the app exits. That
installer's manifest requests administrator, which `CreateProcess` refuses outright, so it is started
through the shell — Windows shows its elevation prompt, and declining it leaves the app running. macOS
only displays the Homebrew command or the release page because this project has no Apple Developer
certificate or notarization; Gatekeeper may require the first launch to be confirmed manually. Linux
only displays the release page: the archive holds a binary rather than a package, so where the previous
copy lives is the reader's business and not this app's to guess.

**Nothing published here is signed.** The Windows installer carries no Authenticode signature, so
Defender SmartScreen shows *"Windows protected your PC"* on a freshly downloaded build until the reader
chooses **More info → Run anyway**. That is the absence of a code-signing certificate, not a fault in the
build — see [Why Windows warns](#why-windows-warns).

## Why Windows warns

Two different Windows dialogs appear around an install, and they have different causes:

| Dialog | Cause | What removes it |
| --- | --- | --- |
| *"Windows protected your PC" — Unknown publisher* | Defender SmartScreen: the downloaded file carries the Mark of the Web and the binary has no Authenticode signature and no download reputation | An OV or EV code-signing certificate, `signtool sign /fd sha256 /tr <timestamp server> /td sha256` over the installer **and** the packaged `vibe-db.exe` |
| *User Account Control — Do you want to allow this app to make changes?* | The NSIS installer's manifest requests administrator, deliberately | Nothing; it is the elevation prompt an installer is supposed to raise |

An **OV** certificate still starts with no reputation, so SmartScreen may keep warning until enough
copies of that signature have been downloaded; an **EV** certificate is trusted immediately. Neither is
free, and neither is set up in this repository — there is no signing step in `.github/workflows/release.yml`
and no certificate in the Actions secrets.

## Local verification

The Wails v2 CLI supports the NSIS installer and universal macOS target:

```powershell
wails build -platform windows/amd64 -nsis
```

```sh
wails build -platform darwin/universal
ditto -c -k --sequesterRsrc --keepParent build/bin/vibe-db.app vibe-db.zip
```

```sh
wails build -platform linux/amd64
tar -czf vibe-db-linux-x64.tar.gz -C build/bin vibe-db
```

The Linux build needs GTK 3 and WebKit2GTK headers present — `libgtk-3-dev libwebkit2gtk-4.0-dev` on
Ubuntu 22.04, which is the runner the release job uses so the binary keeps that glibc floor. A
distribution carrying only WebKit2GTK 4.1 needs `wails build -tags webkit2_41` instead.

Run `go test ./...` before tagging. The updater logic is covered by focused tests in
`internal/update/service_test.go`.
